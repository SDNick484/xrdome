# xrdome Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Linux player that shows SBS VR180 video on Viture Pro XR and XREAL Air 2 Pro glasses with 3DoF head tracking.

**Architecture:** One C process. libmpv decodes (VA-API) and renders each video frame into an FBO texture; a display-rate loop redraws one fullscreen quad per eye, sampling that texture through a half-equirectangular lookup rotated by the latest head pose. Pose comes through a small backend interface; the first backend reads XRLinuxDriver's OpenTrack UDP output.

**Tech Stack:** C11, meson, OpenGL 3.3 core on EGL, libepoxy, SDL2, libmpv, cmocka.

**Spec:** `docs/superpowers/specs/2026-11-11-xrdome-design.md`. Read it before any task.

## Global Constraints

- C11, built with meson. Tests run with `meson test -C build`.
- Binary name `xrdome`. Public C identifiers use the prefix `xrd_` (macros `XRD_`).
- OpenGL 3.3 core profile on EGL. SDL2 with `SDL_HINT_VIDEO_X11_FORCE_EGL=1`. Xorg only.
- Never link against, vendor, or ship `libglasses.so` or any XRLinuxDriver source. XRLinuxDriver is reached over UDP only.
- Internal orientation convention: unit quaternion, world-from-head, GL axes (+x right, +y up, -z forward). Backends convert to it.
- Target output mode: 3840x1080 at 60 Hz, two 1920x1080 eye viewports.
- mpv options fixed by the spec: `vo=libmpv`, `hwdec=vaapi`, `osd-level=0`.
- Pose staleness threshold: 250 ms. Missed-vsync threshold: swap interval over 20 ms. OpenTrack packet size: exactly 52 bytes. Default UDP port: 4242.
- Device FOV (diagonal, 16:9): `viture-pro` 43.0, `xreal-air2pro` 45.0.
- OpenRC and udev only in any system setup text. Editors in instructions are `vim`.
- Out of scope: everything in spec section 2 "Out of scope".

## Review Focus

1. A file that is not 2:1 SBS (for example flat 16:9): must play without crashing and log one warning naming the dimensions. Test in Task 8.
2. Pitch at exactly plus or minus 90 degrees in a UDP packet: the resulting quaternion must be finite and unit length. Test in Task 1.
3. UDP port already bound (second instance, or OpenTrack itself listening): `open` fails with a message naming the port; the player exits non-zero. Test in Task 4.
4. Frame number going backwards (driver restarted): packets are still accepted. Test in Task 4.
5. Video wider or taller than `GL_MAX_TEXTURE_SIZE`: exit non-zero with a message stating both numbers, no GL error spam. Test in Task 8.

**Produces:**

```c
/* pose.h: xrd_pose and xrd_pose_source exactly as in spec 6.2, plus: */
xrd_pose_source *xrd_pose_source_create(const char *spec, char *err, size_t errlen);
   /* spec = "name" or "name:key=val,key=val". Names: "null", "udp-opentrack".

/* opentrack_packet.h */
#define XRD_OT_PACKET_SIZE 52
int xrd_opentrack_parse(const uint8_t *buf, size_t len, double out[6], uint32_t *frame);
   /* out = x,y,z,yaw,pitch,roll. -1 if len != 52 or any double is non-finite. */

/* timing.h */
uint64_t xrd_now_ns(void);   /* CLOCK_MONOTONIC */
```

Angle convention, measured in Task 0 and confirmed in XRLinuxDriver's source: the packet carries the driver's NWU Euler angles unchanged, with `q = Rz_up(yaw) * Ry_left(pitch) * Rx_forward(roll)`. In GL axes (up = +y, left = -x, forward = -z) that is `xrd_quat_from_ypr_deg(yaw, -pitch, -roll)`. The backend applies this mapping first; the `yaw`, `pitch`, `roll` keys then multiply the mapped angles and default to 1. The pose is absolute in the driver's own world frame (level and forward reads roughly yaw -157, roll 180 on the Viture Pro XR), so nothing may assume its world axes; only rotations relative to a reference are meaningful (Task 5).

`latest()` returns 0 and fills `out` when at least one sample has arrived, 1 when none has. The backend thread publishes through a seqlock (one writer, wait-free reader).
